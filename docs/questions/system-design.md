# Plana — вопросы системного дизайна

> **Статус: закрыт.** Все вопросы отвечены 2026-10-09, финальные решения — в `docs/decisions.md`. Документ оставлен как реестр вопросов и обоснований. Примечание: В5 решён иначе, чем рекомендовалось — владелец выбрал oxlint + oxfmt (oxc, VoidZero) вместо Biome; oxfmt 1.0 stable вышел 2026-10-06.

Дата: 2026-10-09. Каждый вопрос снабжён моей рекомендацией (Р). Ответы фиксируем в `docs/decisions.md`.

## Инфраструктура и деплой

**В1. Домены.** Есть ли кастомный домен (например, plana.app)?
Р: начать с `plana.vercel.app` (фронт) + `plana-api.up.railway.app` (API), кастомный домен добавить когда появится: фронт на `plana.app`, API на `api.plana.app`. Vite-приложению домен API приходит через переменную окружения, переезд безболезненный.

**В2. Схема окружений на Vercel.** Варианты: (а) два проекта Vercel — `plana` (production=main) и `plana-dev` (production=develop, стабильный URL для ручного тестирования); (б) один проект, где develop-ветка получает вечные preview-деплои.
Р: вариант (а) — у develop-окружения постоянный URL и «боевой» билд, как у production.

**В3. Окружения на Railway.** Один Railway-проект с двумя environments (develop/production), в каждом свой PostgreSQL + API-сервис. Деплой по пушу в ветку.
Р: да, так и сделать. Backups включить на production-БД.

**В4. CI/CD.** GitHub Actions: на PR — lint + typecheck + тесты + build (обязательный статус-чек); merge в develop → автодеплой в develop-окружения; merge в main (только через PR из develop) → автодеплой в production.
Р: именно так, деплои в production — только через PR develop→main, никаких прямых пушей в main.

**В5. Линтеры/форматирование.** ESLint + Prettier (классика) или Biome 2 (один быстрый инструмент, lint+format вместе)?
Р: Biome — быстрее в CI, меньше конфигов, агентам проще соблюдать один инструмент.

## Архитектура

**В6. Структура репозиториев.** Монорепо pnpm workspaces (`apps/web`, `apps/api`, `packages/shared`, `packages/config`) или два отдельных репо?
Р: монорепо — общий пакет типов/zod-схем, единая версия TS-зависимостей, один PR на фичу сразу для фронта и бэка. Vercel и Railway умеют деплоить по root directory.

**В7. API-стиль.** REST + OpenAPI (типизированный клиент генерируем на фронте) или tRPC?
Р: REST + OpenAPI. Swagger-документация полезна и людям, и агентам; типизированный клиент (openapi-typescript) даёт 90% выгоды tRPC без связывания.

**В8. ORM.** Drizzle или Prisma (см. `docs/research/backend-stack.md`)?
Р: Drizzle.

**В9. Auth в MVP.** (а) email+пароль; (б) только OAuth (Google); (в) оба; (г) внешний сервис (Clerk и т.п.)?
Р: (а) email+пароль со своей реализацией (argon2, access-JWT короткоживущий + refresh-токены в БД с ротацией). Google OAuth добавить после MVP. Своя реализация — без внешних платежей и вендор-lock, и это хорошо изученный агентами паттерн.

**В10. Realtime/синхронизация.** Нужна ли мгновенная синхронизация между вкладками/устройствами в MVP (SSE/WebSocket), или polling каждые N секунд достаточно?
Р: MVP — polling (TanStack Query, refetchInterval при фокусе окна + после мутаций). Если в MVP войдут совместные списки — сразу WebSocket (socket.io в NestJS).

**В11. Фоновые задачи.** Если в MVP есть напоминания — нужен планировщик: отдельный cron-сервис на Railway (каждую минуту ищет сработавшие напоминания) или BullMQ + Redis.
Р: cron-сервис на Railway без Redis — для объёмов MVP достаточно; web push отправляет он же.

**В12. Файловое хранилище** (если в MVP входят вложения): Railway Object Storage (S3-совместимый) или Cloudflare R2?
Р: Railway Object Storage — всё в одной панели и одном биллинге; загрузка через presigned URLs мимо API.

## Продукт и PWA

**В13. Языки интерфейса.** Только русский? Русский + английский с i18n с первого дня?
Р: RU + EN с i18n (react-i18next или lingui) с первого дня — на пустом проекте это дёшево, задним числом дорого.

**В14. Офлайн-режим.** Только PWA-инсталляция + кэш статики (app shell), или полноценный офлайн с локальной БД (IndexedDB) и очередью синхронизации?
Р: MVP — только app shell + онлайн-данные. Полный офлайн — большая отдельная работа (конфликты, sync-протокол), post-MVP.

**В15. Web push-уведомления.** Напоминания пушами в MVP? Технически: service worker + web-push (VAPID), iOS поддерживает с 16.4+ для установленных PWA.
Р: если напоминания входят в MVP — да, web push как единственный канал (email опционально позже).

**В16. Дизайн-система.** Base UI уже решён; вопрос — с shadcn (готовые стилизованные компоненты на Base UI... на октябрь 2026 shadcn поддерживает Base UI как адаптер) или свои компоненты с нуля на Tailwind?
Р: решить на этапе дизайна; технически — Tailwind CSS 4 + Base UI в любом случае.

**В17. Таймзоны.** Все даты в UTC в БД + таймзона в профиле пользователя; повторяющиеся задачи по RRULE, вычисление вхождений в таймзоне пользователя (и пересчёт при смене таймзоны — как у TickTick).
Р: да, это принципиальный вопрос для планировщика, фиксируем сразу.

**В18. Стартовые данные.** Нужен ли seed (демо-списки/задачи) для нового аккаунта?
Р: нет, пустой Inbox; возможно короткий onboarding-чеклист как обычные задачи.

## Качество и наблюдаемость

**В19. Ошибки и мониторинг.** Sentry (self-hosted бесплатно / SaaS платно) или что-то проще (Axiom, GlitchTip)?
Р: Sentry SaaS free tier на старте (5k ошибок/мес) — фронт + бэк.

**В20. Продуктовая аналитика.** Нужна ли (PostHog / Umami / ничего)?
Р: ничего в MVP; добавить позже по необходимости.

**В21. Уровень тестирования MVP.** Юнит-тесты сервисов с логикой (повторы, таймзоны, NLP-парсер) + e2e ключевых API-флоу (auth, CRUD задач) + минимальный Playwright smoke (логин, создать задачу, завершить)?
Р: да, именно такой минимум; покрытие strive к 100% только на логике повторов/дат.
