Источник вопросов: `docs/questions/system-design.md`. Все вопросы закрыты 2026-10-09.

## 2026-10-09 — Часть 1: скоуп и стек (по ответам владельца)

| Решение              | Значение                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Представления задач  | Только list view с группировками (дата/приоритет/тег/список), секциями, drag&drop. Канбан, календарь, матрица Эйзенхауэра — post-MVP |

Следствия: объектное хранилище Railway Object Storage + presigned URLs; cron-воркер на Railway для web push; realtime не нужен — polling (TanStack Query).

## 2026-10-09 — Часть 3: архитектура и скелет монорепо

| Решение              | Значение                                                                                                                                                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frontend-архитектура | **Feature-Sliced Design (FSD) v2** — обязательная методология для `apps/web` (решение владельца). Слои, правила импортов и сегменты: `docs/architecture/frontend.md`                                                        |
| Runtime              | **Node 24 LTS** (обновлено с 22: 24 — активная LTS с октября 2025; локальная версия 24.19; зафиксировано в `.nvmrc`)                                                                                                        |
| Версии стека         | NestJS 12, Vite 8, React 19.3, Drizzle ORM 0.45 + drizzle-kit, zod 4, TanStack Query 5, react-router 8, Vitest 5, oxlint 1.87 + oxfmt 0.72 (npm-пакет oxfmt пока 0.x — 100% Prettier-совместимость по beta-анонсу VoidZero) |
| TypeScript           | **5.9.3**, не 7.x: TS 7 (нативная переработка) уже `latest` в npm, но работа `emitDecoratorMetadata` (DI в NestJS) в ней не подтверждена экосистемой. Миграцию на 7 пересмотреть после стабилизации                         |
| Схема БД             | Утверждена `docs/architecture/erd.md` (16 таблиц; повторяющиеся задачи через RRULE + task_completions; напоминания как offset от времени задачи)                                                                            |
| Структура API        | Утверждена `docs/architecture/api.md` (REST /v1, формат ошибок, auth-флоу c Google OAuth)                                                                                                                                   |
| Скелет монорепо      | Создан и полностью зелёный: oxlint, oxfmt --check, tsc, 7 тестов (shared 3, web 3, api 1 e2e), сборка web (425 КБ js) + api, smoke-проверка `GET /v1/health`                                                                |

Особенности реализации скелета, о которых надо знать агентам:

- `packages/shared` — ESM (`type: module`), поэтому его относительные импорты пишутся с расширением `.js`; api — CommonJS (классический NestJS-стиль), web собирает shared из исходников через alias в `vite.config.ts`.
- Тесты NestJS в Vitest идут через `unplugin-swc` + `.swcrc` (esbuild не умеет `emitDecoratorMetadata`) — конфиг в `apps/api/vitest.config.mts`.
- Dev-режим api — только через `nest start --watch` (`@nestjs/cli`, tsc). Запуск исходников лоадерами (tsx, @swc-node/register) не работает: без `emitDecoratorMetadata` DI NestJS молча подставляет undefined вместо зависимостей, а Node 24 дополнительно парсит `.ts`-entry как ESM. Прод-сборка — `nest build` из `tsconfig.build.json` (спеки и `src/test` в dist не попадают).
- Нативные бинарники: `allowBuilds` в `pnpm-workspace.yaml` (`@swc/core`, `esbuild`).
- Dockerfile API собирается из корня монорепо (`pnpm deploy --prod`) — параметры для Railway в `docs/deploy.md`.

## 2026-10-09 — Часть 5: M2 готов (папки/списки/секции + сайдбар)

| Решение                  | Значение                                                                                                                                                                                                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Семантика `position`     | PATCH с `position` принимает **целевой индекс (0-based)** в контейнере, а не дробное значение. Сервер в транзакции перенумеровывает всех соседей шагом 1024 и проставляет целевую позицию. Списки сортируются внутри контейнера (root или папка), папки — в root, секции — внутри списка |
| Чужие/удалённые сущности | Возврат **404 вместо 403** (не раскрываем существование сущности другим владельцам). К мешанине «чужое» и «в корзине» — одинаковый ответ 404                                                                                                                                             |
| Inbox                    | Системный список, защищён на уровне api: rename / move / delete → **409 CONFLICT**. Создаётся вместе с аккаунтом, `kind = "inbox"`                                                                                                                                                       |
| Корзина (структура)      | Список — мягкое удаление: `trashedAt` списку + всем его незатронутым задачам; restore снимает оба. Папка — физическое удаление, её списки уходят в root (FK SET NULL). Секция — физическое удаление, задачи остаются без секции (FK SET NULL)                                            |
| HTTP-коды                | DELETE → 204 (`@HttpCode`), restore → 200 — явно, у NestJS дефолт 200/201                                                                                                                                                                                                                |
| Изоляция e2e api         | `fileParallelism: false` в `apps/api/vitest.config.mts` (все спеки делят одну БД `plana_test`) + префиксные email (`structure-%`) и адресная очистка в `beforeAll`                                                                                                                       |
| FSD-раскладка структуры  | `entities/list` — `structureKeys` + `useSidebarQuery` (staleTime 60с); `features/structure-manage` — все мутации с инвалидацией сайдбара; `widgets/sidebar` — дерево UI; `app/layouts/app-layout` владеет `<main>`                                                                       |

Проверено: 36 тестов (shared 12, web 3, api 21 e2e), полный зелёный прогон, ручной smoke в браузере (создание папки/списка, inline-переименование, удаление с confirm-диалогом, тёмная тема).

## 2026-10-10 — Часть 6: M3 готов (задачи + подзадачи + умные списки + quick-add)

| Решение                  | Значение                                                                                                                                                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quick-add NLP            | Чистая функция `parseQuickAdd(input, { now, timeZone })` в `packages/shared` — без сети и состояния, переиспользуется вебом (живой предпросмотр) и api (`POST /v1/tasks/parse`). Порядок разбора: приоритет → дата → время                                                                          |
| Грамматика RU            | Приоритет `!`/`!!`/`!!!` отдельным словом → none/low/medium/high. Даты: сегодня/завтра/послезавтра, «через N дней/недель/месяц», «в пн…в вс» (ближайший день, сегодня не считается), «25 декабря»/«25 дек» + год, `дд.мм(.гг\|.гггг)`, ISO. Время: «в 17»/«17:30»                                   |
| Фолбэки дат              | Время без даты → сегодня, если время ещё не прошло, иначе завтра. Дата без года оказалась в прошлом → +1 год (поведение TickTick). Вся строка распарсилась целиком → вернуть исходник без разбора (пользователь писал не дату)                                                                      |
| Границы слов             | `\b` в JS-регексах не работает с кириллицей (word boundary определён через `[A-Za-z0-9_]`) — границы через негативный просмотр `(?![а-яё])`                                                                                                                                                         |
| Календарные дни          | День — строка `YYYY-MM-DD`, арифметика через UTC-полдень. `addMonths` считает year/month вручную с клампом к длине месяца: `setUTCMonth` перескакивает (31 января +1 мес → 3 марта)                                                                                                                 |
| Умные списки             | `today` включает просроченные (.TickTick), `next7 = [today, today+7]` включительно, `inbox` — незавершённые задачи Inbox, `all` — все активные, `completed`/`trash` — плоско по дате DESC. «Сегодня» считается в TZ пользователя (`users.timezone`), сортировка smart: pinned → dueDate → createdAt |
| Контейнер задачи         | `(listId, sectionId)`: `position` — целевой индекс 0-based, перенумерация шагом 1024 в транзакции — та же семантика, что у структуры в M2. При переносе между списками/секциями позиция ставится в конец                                                                                            |
| dueTime только с dueDate | Проверка в create-схеме и merge-проверка на сервере в PATCH (иначе при очистке даты время бы «зависло» без даты — 400)                                                                                                                                                                              |
| GET sections             | Добавлен `GET /v1/lists/:id/sections` (по `position`) — нужен панели деталей; `api.md` обновлён, из его smart-enum убран `recent` (не входит ни в один milestone)                                                                                                                                   |
| FSD-раскладка задач      | `entities/task` — api + `taskKeys` + `useTasksQuery` (staleTime 30с) + `useUserTimezone`; `features/task-manage` — мутации, инвалидируют `taskKeys.all`; `features/quick-add` — поле с живым разбором и chips; `widgets/task-list` — grouping + строки; `widgets/task-details` — правая панель      |
| UX панели деталей        | Desktop — sticky справа (320px) в `.page-columns`, мобильный (≤720px) — fixed снизу. Toggle подзадач виден всегда («▸ +» при нуле) — иначе добавить первую подзадачу неоткуда. Поле «Секция» сбрасывается при смене списка; PATCH шлёт только изменившиеся поля                                     |

Проверено: 93 теста (shared 57, web 3, api 33 e2e), полный зелёный прогон (build web 472.58 kB, gzip 143.65), ручной smoke в браузере: quick-add с NLP («завтра в 17 !!» → завтра 17:00 medium; «через 3 дня» → 13 окт), панель деталей (перенос между smart-списками при смене даты), подзадачи 1/2, завершение/возврат, корзина/восстановление, секции (создание на странице списка + перенос задачи в секцию из панели).

## 2026-10-10 — Часть 7: M4 готов (повторяющиеся задачи, RRULE)

| Решение                  | Значение                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Движок вместо библиотеки | ERD упоминал библиотеку `rrule`, но реализован собственный движок (`packages/shared/src/lib/rrule.ts`): наш домен — календарные дни (YYYY-MM-DD в TZ пользователя), а rrule-библиотека работает в datetime/UTC и месяцы с меньшим числом дней пропускает (31 янв → март), нам нужен кламп (31 янв → 28 фев, поведение TickTick). Формат строки остаётся RFC-5545-совместимым подмножеством — движок заменяем без изменения контрактов |
| Подмножество RRULE       | `FREQ=DAILY/WEEKLY/MONTHLY/YEARLY`, `INTERVAL=1..52`, `BYDAY` (только WEEKLY), `COUNT` (0-based индексация от DTSTART, COUNT включает первое вхождение), `UNTIL` (дата, включительно); COUNT+UNTIL взаимоисключающие; неизвестные ключи/дубликаты → невалидно                                                                                                                                                                         |
| Пропуск просрочки        | Завершение сдвигает dueDate на первое вхождение после `max(dueDate, сегодня)`: ежедневная задача с датой «вчера» при завершении сегодня получает «завтра», а не «сегодня»/«вчера» (TickTick-поведение)                                                                                                                                                                                                                                |
| complete для повторов    | НЕ идемпотентен: каждый вызов закрывает одно вхождение (запись task_completions + сдвиг dueDate). Исчерпание COUNT/UNTIL → `completedAt`, dueDate остаётся на последнем вхождении. Для обычных задач идемпотентность сохранена                                                                                                                                                                                                        |
| uncomplete для повторов  | Удаляет последнюю запись истории (по completedAt DESC), dueDate = её occurrenceDate, completedAt снимается. Пустая история — no-op. Кнопка «Отменить последнее завершение» в панели доступна всегда для повторяющихся задач                                                                                                                                                                                                           |
| Re-anchor                | Смена `rrule` или `dueDate` повторяющейся задачи перезапускает шаблон: `rruleStartDate` = новая дата, история вхождений удаляется (иначе COUNT/откат работали бы от старого якоря). Снятие повтора (`rrule: null`) удаляет и якорь, и историю                                                                                                                                                                                         |
| Повтор требует дату      | `rrule` без `dueDate` → 400: и в create-схеме (refine), и merge-проверкой в PATCH (как dueTime/dueDate из M3). В панели деталей при включении повтора без даты дата автоматически = сегодня в TZ пользователя                                                                                                                                                                                                                         |
| Quick-add повторы        | Токены: «ежедневно/еженедельно/ежемесячно/ежегодно», «по будням» (MO–FR), «по выходным» (SA,SU), «каждый/каждую/каждые N день/неделю/месяц/год/лет», «каждую пятницу» → WEEKLY;BYDAY=код дня. Повтор без даты → сегодня; для BYDAY якорь — первый день шаблона от сегодняшнего (с субботы «по будням» → понедельник), иначе dueDate не был бы вхождением                                                                              |
| Метки повторов           | `rruleLabelRu`/`rruleValueLabel`: «Каждый день», «Каждые 2 недели: пн, ср», «· 3 раза», «· до 31.12.2026» с русскими формами множественного числа. Используются в tooltip бейджа ↻ в строке задачи, chip в quick-add и опциях панели                                                                                                                                                                                                  |
| Completed-список         | Вхождения повторов не показываются в smart=completed (только задачи с completedAt, включая исчерпанные повторы) — отображение истории вхождений post-MVP                                                                                                                                                                                                                                                                              |

Проверено: 132 теста (shared 86, web 3, api 43 e2e, из них 10 на повторы), полный зелёный прогон, ручной smoke в браузере: quick-add («Полив цветов ежедневно в 9» → сегодня 09:00 ↻; «Встреча с ментором каждую пятницу в 18 !!» → 16 окт 18:00, WEEKLY;BYDAY=FR, 🔺), завершение вхождения (задача уехала из «Сегодня» в «Завтра»), откат последнего вхождения (вернулась в «Сегодня»), смена повтора «Каждый день» → «Каждый месяц» через панель.

## 2026-10-10 — Часть 8: M5 готов (теги, поиск, корзина 30 дней, batch, drag&drop)

| Решение                | Значение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| tagNames вместо tagIds | ERD/ТЗ предполагали `tagIds`, реализовано `tagNames: string[]` (до 20, имена): клиенту не нужно знать id тегов, неявное создание покрывает quick-add с хештегами одним запросом, дедупликация по lower(name) бесплатна (уникальный индекс `tags_user_name_lower_idx`).
